# ADT RTS — мастер-план

> Классическая RTS (Warcraft / StarCraft / AoE) внутри раунда SS14: отдельная карта,
> два игрока, сбор ресурсов, база, армия, туман войны, полноэкранный RTS-интерфейс.
>
> Статус: **проектирование**. Код не написан. Документ — источник правды для всех фаз.
> Дата: 2026-08-03.

---

## 0. Краткая формулировка

| Параметр | Значение |
| --- | --- |
| Что это | Мини-игра «раунд в раунде», не геймрул |
| Запуск | `initrts <игрок1> <игрок2> [туман_войны]`, админская команда |
| Кто может играть | **Только призраки.** Живой игрок в матч не попадает |
| Сеттинг | Классическое средневековье/фэнтези (Warcraft / AoE): ратуша, дома, фермы, ополченцы, лучники, катапульты |
| Карта | Отдельный `MapId`, генерируется процедурно (Planet + Biome), удаляется в конце матча |
| Размер арены | 192 × 192 тайла |
| Игроков | 2 (архитектура рассчитана на N, но UI/команда — на 2) |
| Ресурсы | Дерево, Пшеница, Руда |
| Лимит армии | 100 попа (население от домов) |
| Длительность матча | Целевая 25–30 минут |
| Туман войны | Есть, отключаемый третьим аргументом команды |
| Атмосфера | **Отсутствует полностью** — ни на карте, ни в сущностях |
| Влияние на станцию | Нулевое: другая карта, другие слои коллизий, свои системы, свой тикрейт |

### Ключевые архитектурные решения (принятые по умолчанию)

1. **Юниты — не мобы, а сверхлёгкие сущности.** Никаких `DamageableComponent`,
   `MobStateComponent`, `BodyComponent`, `RespiratorComponent`, `BarotraumaComponent`,
   `TemperatureComponent`, `HungerComponent`, `ThirstComponent`, `BloodstreamComponent`.
   Свой `RtsHealthComponent` (int HP + класс брони) и свой урон. Иначе 300 юнитов =
   300 подписок на десятки апстримных систем. Полный чёрный список — §8.7.
2. **Атмосферы нет вообще.** Карта создаётся без атмосферы, сущности не имеют дыхания,
   давления и температуры. Это не оптимизация «на потом», а условие задачи — см. §3.2.
3. **Движение — своё.** Не `InputMover`/`SharedMoverController`. Свой контроллер, пишущий
   `LinearVelocity`, + групповые flow-field'ы вместо per-unit A*.
4. **В RTS входят только призраки.** Живого игрока команда в матч не пустит. Это снимает
   целый класс проблем: тело на станции, SSD, смерть во время матча, конфликт с ролью.
   Управление передаётся из призрака в сущность-камеру, выход — возврат в призрака.
5. **Арена конечная и полностью прогружается один раз.** Биом генерирует terrain, после
   генерации `BiomeComponent` выключается. Даёт стабильную карту для пасфайндинга,
   миникарты и отсутствие подгрузки чанков во время матча.
6. **Сервер авторитетен во всём.** Клиент шлёт только «намерения» (приказ, постройка,
   найм). Выделение юнитов — чисто клиентское, сервер проверяет владение на каждом приказе.
7. **Спрайты — только существующие ассеты SS14.** Новый арт не рисуем и не портируем.
   Подбираем подходящие существующие RSI, при необходимости перекрашиваем в цвет команды.

## 1. Границы и правила проекта

### 1.1. Куда пишем код

```
Content.Shared/ADT/RTS/**
Content.Server/ADT/RTS/**
Content.Client/ADT/RTS/**
Resources/Prototypes/ADT/RTS/**
Resources/Textures/ADT/RTS/**
Resources/Audio/ADT/RTS/**
Resources/Locale/ru-RU/ADT/rts/**
```

Основная масса логики живёт здесь. Но в отличие от обычных ADT-задач, RTS **может править
апстрим** — см. §1.2.

### 1.2. Политика правок апстрима

Решение по проекту: **если правка апстрима проще и быстрее, чем городить обходной путь у себя —
правим апстрим.** Обходные конструкции ради чистоты диффа не строим.

При этом сохраняем практику, уже принятую в проекте (как в потайловом движении, где в
`SharedMoverController` осталось всего три хука):

1. В апстримный файл кладём **минимальный хук** — вызов, проверку флага, точку расширения.
2. Вся логика живёт в ADT-partial или в ADT-системе рядом.
3. Каждая правка апстрима попадает в **реестр ниже** — чтобы при мердже с апстримом
   было понятно, что и зачем мы трогали.

**Реестр правок апстрима** (заполняется по мере реализации):

| Файл | Что меняем | Зачем | Фаза | Статус |
| --- | --- | --- | --- | --- |
| `Content.Client/Input/ContentContexts.cs` | Вызов `RtsFunctions(contexts)` + сам метод: контекст `"rts"` на базе `"common"` | Свободные ЛКМ/ПКМ под выделение и приказы | 2 | **сделано** |
| `Content.Client/Gameplay/GameplayState.cs` | 6 строк в начале `LoadMainScreen`: если игрок в матче — грузим `RtsGameScreen` | Полное скрытие базового HUD | 2 | **сделано** |
| `Resources/keybinds.yml` | Блок дефолтных биндов RTS в конце файла | Хоткеи режима | 2 | **сделано** |
| `Content.Shared/Eye/VisibilityFlags.cs` | Два новых бита `RtsTeamA = 1 << 9`, `RtsTeamB = 1 << 10` | Скрытие вражеских сущностей из PVS | 4 | **сделано** |
| `EscapeUIController`, `SandboxUIController` | Проверки на null у кнопок верхнего меню | Эти кнопки живут в `GameTopMenuBar`, которого нет на RTS-экране; без проверки — NRE при открытии меню | 3 | **сделано** |
| `ContentKeyFunctions` | — | Бинды RTS | 2 | **не понадобилось**: свой `RtsKeyFunctions` в ADT |
| `BiomeSystem` | — | Форс-прогрузка и выключение биома | 1 | **не понадобилось** |

Про биом: правка апстрима оказалась не нужна. `BiomeSystem.ReserveTiles` уже генерирует
тайлы в произвольном прямоугольнике на пустом гриде, а `SetEnabled` публично выключает
дальнейшую подгрузку. Атмосфера снимается обычным `RemComp<MapAtmosphereComponent>`
после `EnsurePlanet`.

### 1.3. Соглашения по коду

- **Сетевой компонент — это `[RegisterComponent, NetworkedComponent, AutoGenerateComponentState]`.**
  Без `NetworkedComponent` генератор состояния молча ничего не даёт: компонент не сетевой,
  на клиент не попадает, и всё, что выставлено на сервере в рантайме, там просто не существует.
  Проявляется особенно подло, когда компонент есть в прототипе: спрайт на месте, сущность
  видна, а все серверные поля — прототипные значения по умолчанию. Именно на этом были
  потеряны часы в фазе 3: `RtsOwnedComponent` навешивался на сервере и до клиента не доезжал,
  поэтому проверка владения всегда была ложной и не выделялось ничего.

- Инлайн-`if` запрещён; `if` всегда двухстрочный (`if (x)` + тело со следующей строки).
- Object initializer разворачивать, а не писать в одну строку.
- **Одна подписка на пару (компонент, событие).** Перед `SubscribeLocalEvent<TComp, TEvent>`
  грепать по репозиторию: дубликат подписки роняет сервер (`Duplicate Subscriptions`).
  В RTS это особенно опасно — систем будет много и они делят компоненты.
- Локализация: пишем `ru-RU`. Файлы `en-US` **не трогаем без явного запроса** — если нужен
  английский, спрашиваем отдельно.

## 2. Жизненный цикл матча

### 2.1. Команда

```
initrts <игрок1> <игрок2> [туман]
```

- `игрок1`, `игрок2` — имена сессий. Автодополнение показывает **только призраков**.
- `туман` — `true` (по умолчанию) / `false`. Выключает и оверлей тумана, и скрытие
  вражеских сущностей, и «память» о постройках — карта видна целиком.
- Права: `AdminFlags.Fun`.
- Валидация:
  - оба игрока онлайн;
  - **оба управляют призраком** (`GhostComponent`); живой игрок — ошибка с внятным текстом
    «игрок X не призрак», а не молчаливый отказ. Насильно призраком не делаем;
  - ни один не находится в другом матче;
  - это не один и тот же игрок дважды.

Сопутствующие команды:

| Команда | Действие |
| --- | --- |
| `endrts [матч]` | Принудительно завершить, вернуть игроков в тела, удалить карту |
| `rtsspectate <игрок>` | Подсадить админа наблюдателем (камера без команды, туман выключен) |
| `rtsdebug <флаг>` | Отладочные оверлеи: сетка проходимости, flow-field, радиусы обзора, тайлы тумана |

### 2.2. Стадии

```
Idle
 └─> Generating   — создаётся карта, генерируется биом, прогружаются чанки, ставятся базы
      └─> Countdown — 5 секунд, игроки уже видят свою базу, приказы заблокированы
           └─> Running — собственно матч
                └─> Finished — экран победы/поражения, 15 секунд
                     └─> Cleanup — игроки возвращаются в тела, карта удаляется
```

Сущность матча: `RtsMatchComponent` на отдельном entity (не на карте — чтобы пережить
пересоздание карты при неудачной генерации). Хранит: `MapId`, список команд, стадию,
seed, флаг тумана, время старта.

### 2.3. Аварийные ситуации

| Событие | Реакция |
| --- | --- |
| Игрок отключился | Пауза матча на 60 сек, потом техническое поражение |
| Игрок вышел из RTS (экшен / Esc → «Покинуть матч») | Считается сдачей, управление возвращается призраку |
| Игрока зареспавнили / вернули в тело, пока он в матче | Матч немедленно завершается сдачей; камера удаляется, чтобы не осталась «висеть» |
| Призрак игрока был удалён (клинап призраков, реюз) | Матч завершается сдачей, ошибка в лог |
| Раунд закончился | `RoundRestartCleanupEvent` → немедленный `Cleanup` всех матчей |
| Генерация карты не сошлась | 5 попыток с новым seed, потом ошибка в консоль, матч не стартует |

## 3. Генерация карты

### 3.1. Пайплайн

1. `MapSystem.CreateMap()` → новая карта, ставим на паузу инициализации.
2. `BiomeSystem.EnsurePlanet(mapUid, template, seed)` — планета получает `MapGridComponent`,
   `BiomeComponent`, гравитацию, свет. *(API уточнить в Фазе 0.)*
3. Шаблон биома — свой, `ADTRtsArena` (`Resources/Prototypes/ADT/RTS/biome_arena.yml`):
   слои тайлов (трава / земля / камень / вода), слой сущностей (деревья, руда, дикая пшеница),
   слой декалей. Никаких данжей и лута из апстримных шаблонов.
4. **Форс-прогрузка ограниченной области**: арена `192 × 192` тайла (≈ конфигурируемо).
   Чанки грузим порциями по N за тик, чтобы не подвесить сервер — стадия `Generating`.
5. **Постобработка** (свой код, поверх биома):
   - Рамка из непроходимых скал по периметру арены — юниты не убегут в бесконечность.
   - Выбор двух стартовых точек: диагонально, на расстоянии ~70 % диагонали арены.
   - Выравнивание площадки под базу (радиус 8 тайлов → проходимый тайл, снос деревьев/руды).
   - **Симметричная раскладка стартовых ресурсов**: точечная симметрия на 180° относительно
     центра арены. У каждого игрока гарантированно: N деревьев, M жил руды, K полян
     под пшеницу в одинаковых относительных позициях. Это обязательное требование
     честности RTS — чистый шум не даёт равных стартов.
   - Проверка связности: flood fill от базы A должен достигать базы B. Не достиг →
     либо прорубаем коридор, либо новый seed.
   - Сохранение снапшота проходимости и цветовой карты для миникарты.
6. Выключение `BiomeComponent` (или `Enabled = false`) — дальше карта статична.

### 3.2. Атмосферы на карте нет

Требование проекта, а не оптимизация: **на RTS-карту атмосфера не добавляется вообще.**

- Не добавляем `GridAtmosphereComponent` — сетка не попадает в очередь симуляции атмоса.
- Не добавляем `MapAtmosphereComponent` — даже «просто воздух» без симуляции не нужен,
  потому что дышать на карте некому (см. §8.7).
- Если `BiomeSystem.EnsurePlanet` навешивает атмосферу сам — **снимаем её сразу после
  генерации**, а лучше добавляем в апстрим флаг/перегрузку «планета без атмосферы»
  (правка апстрима здесь разрешена, см. §1.2) и заносим в реестр.
- Следствия, которые надо проверить в Фазе 1: нет ли систем, падающих на карте без
  атмосферы (пожары, `Flammable`, испарение луж, `IgnitionSource`). Если такие найдутся —
  соответствующие компоненты просто не используем в RTS-контенте.

Проверка приёмки Фазы 1: на карте матча нет ни одной сущности с атмосферными компонентами,
и профайлер атмоса показывает по этой карте ноль.

### 3.3. Что ещё отключаем ради производительности

- Ветер/декомпрессия, пожары, температура.
- Динамическое освещение — по возможности плоский ambient; темноту рисует туман войны.
- Гравитация — включена (нужна, чтобы ничего не «плавало»).
- Слои коллизий: собственные `RtsUnit` / `RtsBuilding` / `RtsTerrain`. С предметами
  и мобами станции пересечений нет по определению (другая карта), но слои — вторая линия обороны.

### 3.4. Данные арены (серверный кэш, не сущности)

```
RtsArenaData
  Vector2i Size
  byte[]   Passability      // 0 = проходимо, 1 = terrain-блок, 2 = здание
  ushort[] ResourceIndex    // ссылка на узел ресурса в тайле
  Color[]  MinimapColors    // генерируется 1 раз, отдаётся клиенту как PNG-подобный блоб
```

Один массив на матч, а не компоненты на тайлах.

## 4. Игрок, камера, ввод

### 4.1. Камера

Сущность `RtsCameraComponent` + `EyeComponent`:

- Без физики, без коллизий, `TransformComponent` на RTS-карте.
- Свободное перемещение: WASD / стрелки, край экрана, средняя кнопка мыши (drag),
  прыжок по клику на миникарту, `Space` — к последнему событию (атака на базу).
- Зум: колесо, ограниченный диапазон (например 1.0 … 2.4), фиксируется в `EyeComponent.Zoom`.
- Границы: камера не выезжает за арену.
- `VisibilityMask` = бит своей команды (см. §6.3).
- Загрузка PVS: камера — единственный «якорь» PVS на RTS-карте.

**Камера — не призрак.** Это принципиально: у `GhostComponent` полный обзор, он видит
невидимое и игнорирует маски видимости, что полностью сломает туман войны. Поэтому мы
не переносим призрака на RTS-карту и не навешиваем на него RTS-компоненты, а создаём
отдельную чистую сущность-камеру с урезанной `VisibilityMask`.

**Вход:** игрок уже призрак → `MindSystem.Visit(mind, cameraUid)`. Призрак остаётся там же,
где был, и просто «замирает». Управление уходит камере.

**Выход:** экшен `ADTRtsLeave` или Esc → «Покинуть матч» → возврат в призрака,
удаление камеры, сдача (если матч ещё идёт).

Раз тела на станции нет вообще, все связанные риски (смерть тела, SSD, кража вещей,
конфликт с ролью, необходимость неуязвимости) из проекта исчезают.

### 4.2. Ввод

Отдельный input-контекст `"rts"` (`IInputManager.Contexts`), активируется вместе с
RTS-экраном. В нём **нет** станционных биндов (использование предмета, контекстное меню,
дроп и т. д.) — это и решает проблему конфликта ПКМ.

| Действие | Бинд |
| --- | --- |
| Выделить / рамка | ЛКМ (drag = рамка) |
| Добавить к выделению | Shift + ЛКМ |
| Выделить всех такого типа на экране | Двойной ЛКМ / Ctrl + ЛКМ |
| Контекстный приказ (идти / атаковать / собирать / чинить) | ПКМ |
| Явная атака по точке (attack-move) | `A` + ЛКМ |
| Стоять на месте / патруль / удерживать | `S` / `P` / `H` |
| Группы управления | Ctrl + 1..9 создать, 1..9 выбрать, двойное нажатие — центрировать |
| Сетка команд | 4 × 3 (позиционные хоткеи, как в SC2) + мнемоники как альтернатива |
| Отмена / очистить | Esc |
| Свободные слоты для алертов | F1 (простаивающий рабочий), F6 (последняя атака) |

Выделение живёт **на клиенте** (`RtsControlSystem`, список `EntityUid`). На сервер уходят
только приказы:

```
RtsOrderEvent { NetEntity[] Units, RtsOrderType Type, NetCoordinates? Target, NetEntity? TargetEntity, bool Queue }
```

Сервер фильтрует список по владению и по стадии матча. Рейт-лимит на приказы (защита
от спама пакетами).

## 5. Интерфейс

Ориентир — скриншот из задачи. Копируем **раскладку и язык интерфейса**, не изометрию.

### 5.1. Подмена HUD

`RtsGameScreen : UIScreen` со своим набором виджетов. При входе в матч —
`_userInterfaceManager.LoadScreen<RtsGameScreen>()`, при выходе — возврат предыдущего экрана.
Базовый HUD (руки, здоровье, алерты, хотбар, инвентарь) не показывается вообще.

Чат: предлагаю **оставить** (свёрнутый виджет справа сверху или по `Enter`) — игрокам нужно
общаться, и админам нужен канал связи. Если хочется полного экрана — выносим в опцию.

```
│ │   6 × 3      │        │  HP-бар │       │ найма  │        │ + туман  │ │
│ └──────────────┘        └────────────────────────┘        └──────────┘ │
└────────────────────────────────────────────────────────────────────────┘
```

**Панель ресурсов (сверху слева).** Строка = иконка + `текущее/максимум` + счётчик
(число рабочих на ресурсе). Отдельная строка населения с другим цветом рамки: `81/85` +
число простаивающих рабочих. Плашка мигает красным при переполнении склада или упоре в лимит попа.

**Сетка команд (снизу слева).** 6 × 3 кнопок. Содержимое зависит от выделения:
- выделен рабочий → вкладки построек (базовые / продвинутые) + «чинить», «стоп», «отмена»;
- выделено здание → доступные к найму юниты и апгрейды с ценой и временем;
- выделены боевые юниты → приказы (атака, удержание, патруль, строй) и способности.
Каждая кнопка: иконка, буква хоткея в углу, стоимость по ховеру, серая при нехватке
ресурсов/требований, «песочные часы» при перезарядке.

**Панель выделения (снизу по центру).**
- 1 юнит: портрет, имя, HP-бар, столбец статов (атака / броня / скорость / дальность),
  панель нёсомого ресурса или очереди производства (для зданий — прогресс-бар + очередь до 5).
- Много юнитов: сетка портретов до 24 штук с мини-HP-барами, клик — выделить одного,
  Ctrl+клик — исключить из выделения.

**Миникарта (снизу справа).** Отдельный `Control` с ручной отрисовкой:
1. Слой террейна — статичная `Texture`, собранная один раз при генерации арены.
2. Слой тумана — `Texture` 1 тексель на тайл, обновляется ~4 Гц (чёрный = не разведано,
   полутон = разведано, прозрачный = видно).
3. Слой объектов — точки: свои (зелёный), враг (красный), ресурсы (жёлтый/серый), нейтралы.
4. Прямоугольник текущего вьюпорта.
5. ЛКМ — переместить камеру, ПКМ — отдать приказ выделенным.
Форма — прямоугольник; «ромб» из скриншота можно дать опцией поворота на 45°,
но он усложняет попадание мышью, по умолчанию — квадрат.

**Панель алертов (справа).** Кнопки-события: «база под атакой», «простаивающие рабочие (N)»,
«постройка завершена». Клик — прыжок камеры к событию.

### 5.3. Передача состояния в UI

Не BUI (это не интерфейс предмета, а полноэкранный HUD). Вместо этого:
- `RtsTeamComponent` с `[AutoNetworkedField]` (ресурсы, лимиты, поп, открытые технологии)
  на сущности команды, PVS-override на сессию владельца — состояние всегда доходит.
- Клиентский `RtsHudSystem` подписан на `AfterAutoHandleState` и обновляет виджеты.
- Тяжёлые/частые данные (туман, миникарта) идут отдельными сжатыми сетевыми сообщениями,
  а не через компоненты.

## 6. Туман войны

Заимствуем подход StationAi (оверлей + серверный расчёт видимых тайлов), но упрощаем расчёт
и уплотняем хранение — у RTS тайлов на порядок больше.

### 6.1. Модель

Три состояния на тайл на команду:
- `Unexplored` — сплошная чернота, миникарта чёрная, ничего не видно.
- `Explored` — затемнение ~55 %, террейн и **запомненные здания** видны, юниты — нет.
- `Visible` — чисто.

Хранение: битовые маски по чанкам 16 × 16 (`ulong[4]` на чанк на состояние).
Для 192 × 192 это 144 чанка × 2 маски — копейки.

### 6.2. Расчёт (сервер)

- Круговой радиус обзора (`RtsVisionComponent.Range`), **без** трассировки препятствий.
  Occlusion как у StationAi — избыточно дорого и для RTS не обязателен.
- Тик 4 Гц. Пересчитываются только «грязные» области: юнит сдвинулся больше чем на тайл,
  юнит появился/умер, здание построено/разрушено.
- Инкрементально: снимаем `Visible` со старых тайлов, ставим на новые, `Explored` только добавляем.
- Дельты (список изменённых чанков) шлются только владельцу команды.

### 6.3. Скрытие вражеских сущностей

Через `VisibilityComponent` слои:

- Команда A = бит `1 << N`, команда B = бит `1 << (N+1)`, наблюдатель = оба.
- Глаз игрока A имеет маску с битом A.
- Юнит команды A всегда имеет бит A. Бит B добавляется/снимается системой видимости,
  когда команда B его видит/теряет.
- Здания в разведанном тумане не скрываются, а «замораживаются» клиентской памятью:
  сервер шлёт снапшот `(позиция, прототип, цвет команды)`, клиент рисует призрак.
  Реальная сущность при этом скрыта — то есть здание не «телепортируется» в глазах врага
  и не палит текущее HP.

При `initrts ... false` вся система выключается: маски не трогаем, оверлей не создаём,
все тайлы `Visible`. Это должно быть настоящим отключением (нулевая нагрузка), а не
«рисуем прозрачный туман».

### 6.4. Отрисовка (клиент)

`RtsFogOverlay : Overlay` (world space):
- Одна текстура арены (например `256 × 256`, R8: 0 / 128 / 255), обновляется по дельтам.
- Шейдер `.swsl` сэмплит её с билинейкой → мягкие края вместо квадратов.
- Регистрация оверлея, привязка к глазу и порядок отрисовки — подсмотреть у `StationAiOverlay`.

## 7. Пасфайндинг и движение

Апстримный `PathfindingSystem` (breadcrumbs + HTN NPC) рассчитан на станцию и десятки NPC —
для сотни юнитов и групповых приказов не подходит. Делаем своё.

### 7.1. Слои

1. **Cost map** — плоский массив проходимости арены (см. §3.3), обновляется при постройке/сносе.
2. **Flow field** — при групповом приказе на точку считается волна Дейкстры от цели по всей
   арене (или по ограниченному боксу), кэшируется по ключу «тайл цели». LRU-кэш на 16 полей,
   инвалидация при изменении проходимости. Все юниты в приказе просто читают вектор из поля.
3. **A\*** — только для одиночных дальних приказов и для сущностей, которым flow-field
   избыточен (одинокий рабочий к дереву). Ограничение по числу раскрытых узлов за тик.
4. **Локальное расхождение** — простое разделение соседей через `EntityLookup`/spatial hash:
   отталкивание от юнитов ближе радиуса, скольжение вдоль стен. Не полноценный RVO.

### 7.2. Движение

`RtsMovementSystem` (серверный, 30 Гц или ниже):
- Читает желаемое направление (flow field / путь / преследование), пишет `LinearVelocity`.
- Ускорение/торможение, поворот спрайта по 8 (или 4) направлениям.
- Физика: динамическое тело в своих слоях коллизий, сон при простое.
- Клиент — стандартная интерполяция трансформа, никакого предсказания (это RTS, задержка
  приказа в 100 мс незаметна).

### 7.3. Бюджеты

| Что | Частота | Лимит |
| --- | --- | --- |
| Движение | 30 Гц | все юниты |
| FSM юнита (что делать дальше) | 10 Гц, шардировано по 4 группам | все юниты |
| Поиск цели для автоатаки | 4 Гц | только юниты в состоянии Idle/AttackMove |
| Туман | 4 Гц | инкрементально |
| Экономика (тик добычи, найм, стройка) | 2 Гц | все здания |
| Flow field | по требованию | ≤ 2 пересчёта за тик |

Целевой потолок матча: **≤ 500 сущностей** (2 × ~120 юнитов, ~60 зданий, ~150 узлов ресурсов).

## 8. Игровое содержание

### 8.1. Ресурсы

| Ресурс | Источник | Куда сдавать | На что тратится |
| --- | --- | --- | --- |
| **Дерево** | Деревья (пул ~120 ед. на дерево) | Ратуша, Лесопилка | Здания, стрелки, осада |
| **Пшеница** | Фермы (генерирует со временем), дикие поля | Ратуша, Амбар | Найм юнитов, содержание, рабочие |
| **Руда** | Рудные жилы (пул ~800 ед.) | Ратуша, Шахта | Боевые юниты, апгрейды, T2/T3 |

Механика добычи: рабочий идёт к узлу → цикл добычи (2.5 сек) → несёт 10 единиц →
идёт к ближайшей точке сдачи → повторяет. Узел истощается и исчезает (дерево → пень).
Рабочий сам ищет новый ближайший узел того же типа.

Складской лимит (как на скриншоте `31284/36000`): базовый 10 000, каждый склад/амбар +5000,
максимум 36 000. Переполнение — ресурс просто не начисляется, панель мигает.

### 8.2. Население

`81/85` — текущее / лимит. Лимит: Ратуша даёт 10, каждый Дом +5, жёсткий потолок 100.
Каждый юнит стоит 1–4 попа (рабочий 1, пехота 2, кавалерия 3, осада 4).
Третья цифра в строке (`32`) — простаивающие рабочие, кликабельно.

### 8.5. Состояния юнита (FSM)

```
Idle ─┬─> Moving ──> Idle
      ├─> AttackMove ──> Attacking ──> AttackMove
      ├─> Attacking (цель) ──> Idle | Chasing
      ├─> Gathering ──> Returning ──> Gathering
      ├─> Building ──> Idle
      ├─> Repairing ──> Idle
      ├─> Following ──> ...
      └─> HoldPosition (не двигается, атакует в радиусе)
```

Очередь приказов (Shift) — до 8 в очереди. Точка сбора (rally point) у зданий: обычная точка
или ресурсный узел (тогда новый рабочий сразу идёт добывать).

### 8.6. Победа

- Основное: уничтожены все здания противника **и** нет рабочих → поражение.
- Сдача: команда `/surrender` или кнопка в меню (Esc).
- Дисконнект > 60 сек — техническое поражение.
- Опционально: таймер матча (по умолчанию выключен), при истечении — победа по очкам
  (собрано ресурсов + убито юнитов + построено зданий).

Балансная цель: средний матч 1v1 длится **25–30 минут** от старта до уничтожения базы.
Всё, что систематически даёт 10-минутные или часовые партии, правим в Фазе 10.

### 8.7. Состав RTS-сущности (чёрный список компонентов)

Ключевое требование производительности. RTS-юнит — это **не моб**, а минимальная сущность.

**Разрешено на юните:**

| Компонент | Зачем |
| --- | --- |
| `TransformComponent` | Позиция |
| `SpriteComponent` | Отрисовка |
| `PhysicsComponent` + `FixturesComponent` | Коллизии в своих слоях, толкание юнитов |
| `RtsOwnedComponent` | Принадлежность команде |
| `RtsHealthComponent` | HP, максимум, класс брони, регенерация |
| `RtsSelectableComponent` | Выделение и маркер |
| `RtsMovementComponent` | Скорость, ускорение |
| `RtsOrderQueueComponent` | Приказы и состояние FSM |
| `RtsCombatComponent` | Только у боевых |
| `RtsGathererComponent` | Только у рабочих |
| `RtsVisionComponent` | Радиус обзора |
| `VisibilityComponent` | Скрытие от врага |
| `MetaDataComponent` | Обязателен движком |

**Запрещено (чёрный список).** Ни один прототип в `Resources/Prototypes/ADT/RTS/` не должен
содержать:

- Атмос и физиология: `RespiratorComponent`, `BarotraumaComponent`, `TemperatureComponent`,
  `InternalsComponent`, `LungsComponent`, `BloodstreamComponent`, `HungerComponent`,
  `ThirstComponent`, `PerishableComponent`, `FlammableComponent`.
- Мобное: `MobStateComponent`, `MobThresholdsComponent`, `DamageableComponent`,
  `BodyComponent`, `StaminaComponent`, `StatusEffectsComponent`, `MovementSpeedModifierComponent`.
- Взаимодействие со станцией: `InputMoverComponent`, `InventoryComponent`, `HandsComponent`,
  `ItemComponent`, `StorageComponent`, `PullableComponent`, `ClimbingComponent`,
  `ButtCheckComponent` и прочие интеракционные.
- ИИ и речь: `HTNComponent`, `NPCUseActionOnTargetComponent`, `SpeechComponent`,
  `EmotingComponent`, `ExaminableComponent`.
- Тяжёлое визуальное: `AppearanceComponent` без нужды, `PointLightComponent` на каждом юните
  (свет — только у нескольких зданий, и то под вопрос).

**Здания** отличаются от юнитов только заменой `RtsMovementComponent` на
`RtsBuildingComponent`/`RtsConstructionComponent` и статической фикстурой. Тот же чёрный
список действует и для них: горящих, разгерметизирующихся и дышащих зданий у нас нет.

**Проверка приёмки Фазы 3 и Фазы 10:** интеграционный тест проходит по всем прототипам с
`RtsOwnedComponent` и падает, если найден компонент из чёрного списка. Список ведётся в
одном месте, чтобы правило не размывалось со временем.

### Фаза 2 — Камера и HUD-каркас
- `RtsCameraComponent`, движение, зум, границы, прыжок по миникарте (заглушка).
- Input-контекст `"rts"`, все бинды.
- `RtsGameScreen`, скрытие базового HUD, возврат прежнего экрана при выходе.
- Пустые виджеты: панель ресурсов, сетка команд, панель выделения, миникарта, алерты.

**Готово когда:** игрок летает над сгенерированной ареной в RTS-интерфейсе, базовый HUD
не виден, выход возвращает всё как было — в том числе при раунд-рестарте, при принудительном
респавне призрака админом и при дисконнекте посреди матча.

**Выяснено при реализации.** Кастомный `UIScreen` обязан содержать три вещи, иначе апстримные
контроллеры падают на `_loadController.LoadScreen()`:
`LayoutContainer` с именем `ViewportContainer` (его ищет `ChatUIController.OnScreenLoad`),
виджет `ChatBox` (иначе `SetMainChat` кидает исключение в `default`-ветке) и `MainViewport`
(его дёргает `GameplayState.Viewport`). Остальные контроллеры — хотбар, инвентарь, действия,
алерты, призрак, верхнее меню — к отсутствию своих виджетов относятся спокойно.
Это и решает вопрос §12.2.1: чат в RTS остаётся, потому что он ещё и технически обязателен.

**Правило конфликтов хоткеев** (выяснено на плейтесте фазы 2). Контекст `"rts"` наследует
`"common"`, поэтому бинд конфликтует ровно тогда, когда пересекается с функцией из `common`
или из глобальных биндов движка. С функциями из `"human"` пересекаться **можно** — этот
контекст в RTS не активен, поэтому `V`, `X`, `H`, `Z` спокойно дублируют станционные клавиши.

Занято в `common` и движком: F1 (AHelp), F2 (скриншот), F3 (дебаг-мониторы), F4 (HideUI),
F5–F9 (спавнеры, админка, итоги раунда), F10 (меню), F11 (фуллскрин), `B` (песочница),
`P` (копирование объекта), `Period` и `Comma` (фокус чата), цифры 1–9 (хотбар — важно
помнить в фазе 8, когда понадобятся контрол-группы).

Итоговые бинды фазы 2: ЛКМ/ПКМ — выделение и приказ, `V` — атака по точке, `X` — стоп,
`H` — удержание, `Z` — патруль, `Пробел` — простаивающий рабочий, `` ` `` — последнее
событие, `Insert` — покинуть матч. Финальная сетка в стиле SC2 выбирается в фазе 8.

**Границы арены — физика, а не подрезание координаты.** Первая версия клампила позицию
камеры каждый тик в общей системе. На клиенте это выглядит рывками: предсказание уводит
камеру за край, состояние сервера возвращает назад. Заменено на невидимую статическую
рамку `ADTRtsArenaBorder` с четырьмя фикстурами по периметру (маска `GhostImpassable`,
камера уже на этом слое). Физика предсказывается штатно, упор в границу стал плавным.

**Наследование контекста ввода отменить нельзя.** Оба перегруза
`IInputContextContainer.New` требуют родителя; контекст без родителя создаёт только сам
движок и только один раз — для `"common"`. `RemoveFunction` чистит лишь собственный список
контекста, а фильтрация идёт через `FunctionExistsHierarchy`, которая поднимается до корня.

Решение — приоритеты. `InputManager` перебирает биндинги от большего `priority` к меньшему и
останавливается на первом, пометившем событие обработанным (`InputCmdHandler.FromDelegate`
помечает по умолчанию). Функция **без** зарегистрированного обработчика ничего не помечает и
проваливается в станционный бинд. Поэтому RTS-клавиши можно вешать поверх `common` заранее:
до появления обработчика они ведут себя как обычные станционные, а после — перехватываются,
и только внутри контекста `"rts"`.

Исключение: `RtsLeaveMatch` обработчик уже имеет, поэтому F10 в матче не открывает меню
Escape. Меню остаётся на Escape, выход продублирован кнопкой в панели справа.

**Как мышь на самом деле попадает в мир** (стоило двух неверных попыток, поэтому подробно).

`MainViewport` содержит `ScalingViewport` с `MouseFilter = Stop`. Над игровым миром именно
он выигрывает хит-тест, и он же сам пробрасывает клик в мир через `ViewportKeyEvent`.
Отсюда два следствия, которые выглядят противоречиво, но объясняются одной строчкой:

- `KeyBindDown` **никогда** не доходит до нашего экрана: `_doGuiInput` идёт без
  `ignoreStop` и обрывается на `ScalingViewport`. Обрабатывать мышь в `RtsGameScreen`
  бессмысленно — код просто не вызывается.
- `MouseWheel` **доходит**: `_doMouseGuiInput` вызывается с `ignoreStop: true` и всплывает
  сквозь `Stop` до экрана. Ровно поэтому экрану нужен `MouseFilter = Pass`, и ровно поэтому
  колесо работало, когда выделение не работало.

Итог: выделение и приказы — обычные `CommandBinds` с `PointerStateInputCmdHandler`, как
любое другое мировое взаимодействие. `MouseFilter = Pass` на экране оставлен ради колеса и
кликам не мешает. Клик доходит по цепочке
`ScalingViewport.KeyBindDown` → `IInputManager.ViewportKeyEvent(this, args)` →
`GameplayStateBase.OnKeyBindStateChanged` → `InputSystem.HandleInputCommand` → обработчик.
Важно: `ScalingViewport` здесь **контентный** (`Content.Client/Viewport/`), а не движковый.

**`outsidePrediction: true` обязателен для мышиных обработчиков.** Дефолты в движке
несимметричны: у `InputCmdHandler.FromDelegate` это `true`, а у `PointerInputCmdHandler`
и `PointerStateInputCmdHandler` — `false`. В `InputSystem.HandleInputCommand` стоит
`if (!IsPredictionEnabled && !handler.FireOutsidePrediction) continue;`, поэтому мышиные
обработчики молча пропускались, пока клавиатурные работали. Ровно отсюда брался симптом
«клавиши работают, мышь мертва и без единой строчки в логе». Весь контентный клиентский
код (`ConstructionSystem`, `GameplayStateBase`) ставит этот флаг явно — и мы теперь тоже.

**Не гасить жест на нажатии.** Проверка «есть ли команда» стояла в обработчике нажатия и
возвращала false, если состояние камеры ещё не доехало. `DragStart` не выставлялся,
отпускание уходило в никуда, и ввод выглядел полностью мёртвым. Проверки владения должны
стоять там, где реально решается «своё или чужое», а не на входе в жест.

Панели HUD получают `MouseFilterMode.Stop`, иначе клик по интерфейсу выделял бы юнитов
сквозь панель.

**Не полагаться на сущность команды на клиенте.** Сущность с `RtsTeamComponent` живёт в
нулевом пространстве, и рассчитывать, что клиент её получит, нельзя. Поэтому «своё или
чужое» определяется по числовому `TeamIndex`, продублированному в `RtsCameraComponent`
и `RtsOwnedComponent`, а не сравнением `EntityUid` команд.

**Зум колесом — две отдельные причины, почему не работало.**
1. Колеса нет в перечислении клавиш движка, забиндить через `keybinds.yml` невозможно —
   оно приходит только UI-событием. Ловим `MouseWheel` на `RtsGameScreen`.
2. `Control.MouseFilter` по умолчанию `Ignore`, а разводка UI-событий вызывает `MouseWheel`
   только у контролов с фильтром не `Ignore`. Экрану нужен `MouseFilterMode.Pass`.
   Именно `Pass`, а не `Stop`: на биндах `Stop` съедал бы клики, нужные миру для выделения
   и приказов, а `Pass` сам по себе ничего обработанным не помечает.

Применяем зум через `ContentEyeSystem.RequestZoom` (предсказываемое событие), а не через
`SetZoom` напрямую: прямой вызов на клиенте затирается следующим состоянием сервера.
К `EyeComponent.Zoom` значение подтягивает `EyeLerpingSystem`, отсюда плавность.
Шаг колеса 1.12 вместо штатного 1.5 — тот слишком грубый.

Мелочь на будущее: в `Keyboard.Key` клавиша `` ` `` называется `Tilde`, не `Grave`.

### Фаза 3 — Юниты, выделение, движение
- Лёгкий прототип юнита (без мобных компонентов), спавн стартовой базы и 5 рабочих.
- Выделение: клик, рамка, Shift, двойной клик, группы управления.
- Оверлей выделения (зелёные скобки/круги как на скриншоте) и HP-бары над юнитами.
- Приказ движения, cost map, flow fields, локальное расхождение.
- Панель выделения показывает реальный юнит.

**Готово когда:** 60 юнитов по одному приказу идут через препятствия к точке, не слипаются
в кучу, не застревают в стенах; 200 юнитов в движении держат тикрейт.

**Решения по столкновениям.** Юниты и здания получают фикстуру со слоем `GhostImpassable`
и **пустой маской**. Это даёт ровно нужный набор: юнит упирается в границу арены (у неё
`GhostImpassable` в маске), но не сталкивается ни с другими юнитами, ни с камерой.
Разводит юнитов мягкая сила расталкивания в `RtsMovementSystem` — жёсткие столкновения
кинематических тел без апстримного `MobCollision` дают заторы. `MobLayer` не годится:
он включает `Opaque`, то есть юниты перекрывали бы свет.

Здания в этой фазе проход не блокируют. В фазе 6 они начнут закрывать тайлы в костмапе,
и юниты будут обходить их через flow field, а не упираться телами.

**Flow field.** Волна считается с одинаковой стоимостью для всех восьми направлений:
диагонали выходят чуть дешевле правды, но на глаз это незаметно, а поле строится вдвое
быстрее честного Дейкстры с очередью с приоритетом. Уточнение стоимости — фаза 10.
Ближе 2.5 тайлов до цели юнит переключается с поля на прямое движение: поле даёт
направление по центрам тайлов и у самой цели выглядит ступенчато.

Радиус прибытия растёт от размера группы (`0.35 + sqrt(N) * 0.28`): двадцать юнитов
физически не встанут в один тайл, и без запаса они вечно толкались бы у точки приказа.

### Фаза 4 — Туман войны и миникарта
- Серверный расчёт видимости, битовые маски, дельты.
- Слои видимости для скрытия вражеских сущностей, «память» о зданиях.
- Клиентский оверлей + шейдер.
- Полноценная миникарта: террейн, туман, точки, вьюпорт, ЛКМ/ПКМ.
- Флаг `initrts ... false` реально отключает подсистему.

**Готово когда:** игрок A не видит юниты игрока B вне обзора **и в сетевом трафике их нет**;
разведанное здание остаётся призраком; с `false` карта видна целиком и профайлер показывает
нулевую нагрузку от системы видимости.

**Сделано (первый срез).** Серверный расчёт обзора (`RtsVisionSystem`, 4 Гц), хранение
тумана по байту на тайл (`RtsFogData`), скрытие вражеских сущностей через слои видимости
с гистерезисом в 2 секунды, маска глаза на камере, биты `RtsTeamA`/`RtsTeamB` в апстримном
`VisibilityFlags`. Ключевой момент: RTS-сущности **не имеют** слоя `Normal` — иначе их
увидел бы любой, у кого он в маске, и туман потерял бы смысл.

**Сделано (второй срез).** Клиентский туман и его отрисовка. Ключевое решение: **туман по
сети не передаётся вовсе**. Сервер уже прячет вражеские сущности через PVS, поэтому у клиента
есть ровно те входные данные, из которых туман и считается, — свои юниты и их радиусы обзора.
Считать то же самое локально дешевле, чем гонять 36 килобайт на каждый пересчёт, и
рассинхрону взяться неоткуда. Это отменяет пункт про «дельты и сжатые сетевые сообщения»
из §6.2 и §13.

Отрисовка — прямоугольниками, а не текстурой с шейдером: обходим только тайлы в кадре и
склеиваем подряд идущие одинаковые тайлы строки в один прямоугольник, получается несколько
десятков вызовов на кадр. Края выходят по-тайловыми; мягкая растушёвка — задача полировки.

**Осталось в фазе 4:** «память» о разведанных зданиях и отрисовка миникарты.

## 11. Риски

| Риск | Влияние | Что делаем |
| --- | --- | --- |
| Биом не даёт нужного контроля над террейном / не выключается | Высокое | Правим `BiomeSystem` в апстриме (разрешено, §1.2). Запасной план: генерировать арену полностью своим кодом поверх пустого грида, биом использовать только как источник тайл-сетов |
| PVS не тянет 300 сущностей на одного игрока | Высокое | Урезание лимита армии, агрессивный PVS-бюджет для RTS-камеры, отказ от `VisibilityLayers` в пользу чисто клиентского скрытия |
| Скрытие врагов через `VisibilityComponent` вызывает мигание/дорогие PVS-пересчёты | Среднее | Гистерезис (терять видимость с задержкой 2 сек), редкое обновление слоёв |
| ПКМ конфликтует со станционными биндами | Среднее | Отдельный input-контекст (уже в плане), проверить в Фазе 2 |
| Смена `UIScreen` ломается при респавне/раунд-рестарте | Среднее | Восстановление экрана по нескольким триггерам + защитный `try/finally` в выходе из матча |
| Пасфайндинг съедает CPU | Среднее | Жёсткие бюджеты (§7.3), кэш flow-field'ов, деградация до «идти напрямую» при перегрузке |
| Существующих ассетов не хватает на средневековый сеттинг, юниты визуально неразличимы | Среднее | Цвет команды через shader + разные силуэты при подборе; если два юнита неотличимы — меняем подбор, а не рисуем новое. Различимость проверяется на плейтестах Фазы 9 |
| Правки апстрима конфликтуют при мердже с upstream | Среднее | Минимальные хуки вместо переписывания (§1.2), реестр правок, логика в ADT-partial |
| `GhostComponent` видит сквозь туман, если случайно окажется на RTS-карте | Среднее | Камера — отдельная сущность, не призрак (§4.1); тест: призрак не может быть перемещён на карту матча |
| Раздувание скоупа (герои, магия, кампания) | Среднее | Всё сверх §8 — только после Фазы 10 |

## 12. Вопросы

| Вопрос | Решение |
| --- | --- |
| Сеттинг | Классическое средневековье/фэнтези |

### 12.2. Осталось открытым (не блокирует Фазу 0–1)

1. ~~**Чат в RTS-режиме**~~ — решено в фазе 2: остаётся. Виджет `ChatBox` технически

## 13. Приложение — что уточнить в коде (заполняется в Фазе 0)

Выяснено в Фазе 0:

- [x] `BiomeSystem.EnsurePlanet(mapUid, template, seed?, metadata?, mapLight?, dayCycle)` —
      вешает `MapGridComponent`, `BiomeComponent`, гравитацию, `MapLightComponent`, `RoofComponent`,
      `SunShadowComponent` и атмосферу через `SetMapAtmosphere`.
- [x] Форс-прогрузка области — `BiomeSystem.ReserveTiles(mapUid, Box2, List<(Vector2i, Tile)>)`.
      Работает на пустом гриде: `GetLocalTilesIntersecting(..., ignoreEmpty: false)` перебирает
      диапазон координат, а не существующие чанки, поэтому тайлы реально создаются.
- [x] Выключение подгрузки — `BiomeSystem.SetEnabled(ent, false)`, апстрим править не нужно.
- [x] Атмосфера снимается `RemComp<MapAtmosphereComponent>` (`Content.Shared.Atmos.Components`)
      сразу после `EnsurePlanet`.
- [x] Свободные биты `VisibilityFlags`: заняты до `1 << 8` (Bubblegum), свободны `1 << 9` и дальше.
- [x] `MindSystem.Visit(mindId, entity)` отказывает, если `mind.VisitingEntity != null`
      (админ-призрак уже занимает механизм) — проверяем это при валидации команды.
      `UnVisit` возвращает управление `mind.OwnedEntity`, то есть призраку.
- [x] Приоритет слоёв биома: `TryGetTile` идёт по списку **с конца**, поэтому базовый слой
      кладём первым, а самый приоритетный — последним.
- [x] Команды с внедрением систем — наследовать `LocalizedEntityCommands`, требует
      loc-ключи `cmd-<команда>-desc` и `cmd-<команда>-help`.
